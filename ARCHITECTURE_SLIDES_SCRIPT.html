Clinical Co-Pilot — Speaker Script

Sixteen slides, roughly fourteen minutes at a conversational pace. Each cue below gives the words for one slide; the “anticipate” notes flag the question that slide tends to draw.

Slide 01

Title

~30s

On slide: three boxes — chart panel → agent service → FHIR API.

This is the Clinical Co-Pilot: a conversational agent that lives inside the patient chart in our OpenEMR fork. It exists to answer one question — “what do I need to know about this patient right now?” — in seconds, and with every clinical claim cited to a specific record.

The three boxes on screen are the whole story in miniature: a panel in the chart asks, a separate agent service thinks and verifies, and the EMR itself decides what data anyone gets to see. The next fifteen slides unpack why each of those boundaries sits where it does.

Slide 02

The moment

~40s

On slide: 90-second timeline between patients; question in, cited answer out.

Everything in this architecture is shaped by one workflow moment: a primary care physician doing pre-visit review, in the roughly ninety seconds between one patient leaving and the next walking in. The chart is already open.

That window disqualifies a lot of designs up front. A separate app with its own login is dead on arrival — the context switch alone eats the window. So the co-pilot is embedded where the physician already is, and the entire latency and trust budget is spent on answering fast and answering verifiably.

Slide 03

The shape

~60s

On slide: OpenEMR boundary (panel, OAuth, FHIR+ACL, audit log) beside the Python agent service (loop, tools, verification), with LLM and traces outside.

The system is two pieces. On the left, a thin custom module inside OpenEMR — it uses the sanctioned card-render hook the shipped dashboard module already uses, so there are no core edits. It draws the chat panel and inherits the logged-in session. On the right, a separate Python service built on FastAPI: the LLM orchestration loop, a small registry of read-only tools, and a verification layer, with real health and readiness endpoints.

I explicitly rejected running the agent in-process in PHP, for three reasons: PHP’s agent and observability ecosystem is weak; long LLM calls would pin Apache workers; and a separate service scales independently and gives me a clean trust boundary I can point at.

Anticipate “Why not a framework like LangGraph?” — held for slide 13; short answer: one agent and six tools don’t need one.

Slide 04

Authorization

~60s

On slide: physician → SMART token (user + patient) → agent → EMR decides; direct-SQL path struck out.

The most important design decision: the agent has no authority of its own. When the panel starts a conversation it hands the service a SMART-on-FHIR token bound to two things — the logged-in user and the currently open patient. Every single read the agent makes presents that token to OpenEMR’s FHIR API, so the EMR’s existing ACL engine and OAuth scope enforcement make every access decision. A nurse’s token sees exactly what a nurse sees.

The agent holds no database credentials and no service account. And it’s patient-context-bound: it can only be invoked from an open chart, and only queries that patient.

One limitation stated up front: OpenEMR’s ACL is role-based, not panel-based — any role with chart access can open any chart. The agent inherits exactly that boundary. It doesn’t widen the aperture, and it doesn’t narrow it either. We’ll come back to that on the limits slide.

Slide 05

Read-only

~45s

On slide: the six read-only tools feeding the chart; a write tool crossed out.

Version one has zero write access to the EMR. The reasoning is blunt: a read-only agent can produce a bad summary; a writing agent can corrupt a chart. Those are different classes of harm, and we only accept the first.

Read-only also collapses most of the prompt-injection problem. Chart content — notes, scanned documents — is treated as untrusted input, because a document could contain adversarial text. But injected instructions have no write tools to escalate into. The worst an injection can do is bias what a summary emphasizes, and that residual risk is tested with adversarial documents in the eval suite rather than claimed solved.

Slide 06

Verification

~85s

On slide: pipeline from tool results → cited draft → deterministic checker → ship or fail closed; two cards splitting grounding from entailment.

Trust is the product, so the verification layer was designed before the agent loop, not bolted on after. It works like this: tools return structured FHIR resources, and every resource carries its ID. The system prompt requires a citation on every clinical claim. Then a post-processor — not an LLM, ordinary deterministic code — checks that every cited ID actually appeared in this request’s tool results. It costs milliseconds and it cannot itself hallucinate. Where a claim contains a parseable number, value, unit, or date, that’s also compared against the cited resource’s fields.

Failures fail closed: a claim citing an unknown ID is stripped and the response annotated; if stripping guts the response, the user gets “couldn’t verify — view source records” with deep links instead. Medication answers additionally run through OpenEMR’s own drug-interaction and clinical-decision rules, with flags attributed to the EMR’s CDS, not the agent’s judgment. One dependency stated plainly: those checks are only as strong as the medication coding beneath them, and the audit found mostly uncoded free-text meds — so an uncoded medication is flagged “interaction check unavailable,” never silently passed as clean.

And here’s the honest boundary: this verifies grounding, not entailment. The model could cite a real lab and misstate its direction. Catching that in-path would mean an LLM judge on every request — roughly doubling latency and adding a second model to trust — so semantic checking lives in the offline eval suite, which is weighted toward exactly this failure class. I can state precisely what the verifier catches and what it does not.

Slide 07

Speed

~50s

On slide: snapshot fan-out to six fetches; latency target bars (3 / 5 / 10 / 15 seconds).

The default question is served by a single tool, get_patient_snapshot, which fans out in parallel to demographics, meds, problems, allergies, recent labs, and the last encounter — so the common case costs one agent step, not five sequential tool calls. Deeper questions trigger targeted tools on demand; we don’t exhaustively mine the chart up front.

The targets: first token under three seconds, complete snapshot under ten, follow-ups under five, p95 under fifteen. I want to be careful here — these are design targets pending load testing, not measurements. Streaming means reading starts before generation ends, and a cheaper model tier handles routing while a stronger tier writes the synthesis. The tradeoff is explicit: fast-and-explicit beats slow-and-complete — partial results always say what’s missing.

Slide 08

What the audit changed

~65s

On slide: six request lanes each paying a “reload ~500 globals” tax; the promoted fix and two consequences.

This slide is where reading the actual codebase changed the plan. The latency floor is not the FHIR queries — that layer is single-query, not N-plus-one. It’s OpenEMR’s per-request bootstrap: globals.php reloads about five hundred settings from the database on every request. So my six-way parallel fan-out pays that hundred-to-three-hundred-millisecond tax six times, with zero reuse. Parallelism helps wall-clock time but does nothing about that fixed cost.

Four consequences. A bootstrap short-circuit for token-authenticated FHIR requests is the highest-leverage optimization, so it’s promoted to an early task, not deferred to some scale tier. Labs are the slowest resource — the results table has no patient index, it’s a three-table join to reach the patient — so labs get their own timeout and degrade gracefully. The snapshot never requests provenance inlined, because that doubles row work. And encounter content lives in a table-per-form design where assembly costs one query per form — so the interval-change tool returns encounter metadata and notes in bounded batches, keeping full content behind an explicit follow-up.

Slide 09

Failure modes

~55s

On slide: the invariant as a headline; four failure cards.

One invariant governs every failure mode: the physician always knows what the agent did not check. A summary that omits a section must be distinguishable from a summary that verified the section is empty.

So: if the labs fetch fails, the answer ships with the remaining data and an explicit banner — “labs unavailable; this covers meds, problems, allergies” — never a silently narrower summary. If the LLM provider is down or slow, the panel falls back to a plain structured snapshot rendered straight from FHIR data — you don’t need a model to show a med list. Verification failures fail closed, as we saw. And an empty record is stated affirmatively — “no encounters on file since 2023” — because absence of data is itself clinical information. Under all of it, every model output is schema-validated at every step: parse failure means one retry, then the fallback.

Slide 10

Audit trail

~80s

On slide: access log and decision/disclosure log converging on the EMR audit log via the audit bridge; correlation-ID band.

Accountability uses two mechanisms that land in one trail, joined by a correlation ID that appears on every log line, tool call, and trace.

The first mechanism is free: every tool call is just a FHIR request as the authenticated user, so OpenEMR’s existing audit machinery logs the data access natively — no new code. But that’s only an access log. It records that a token read a patient; it doesn’t record that an AI mediated the access, what was asked, what was answered, or whether verification passed. That’s the gap the second mechanism fills: the module exposes a small internal audit bridge, the agent service POSTs the invocation record, and the module writes it through the EMR’s own audit logger, in-process, with a custom event type.

One more thing the bridge records: sending patient data to the LLM is a HIPAA disclosure to a business associate, and OpenEMR already models that — so the bridge calls the existing disclosure-accounting hook, recording recipient, patient, and the minimum-necessary payload actually sent. If the audit POST itself fails, the response is not blocked — service logs plus the EMR row are the durable record — but an alert fires. Fail-closed is for verification; audit delivery is fail-open-with-alarm. And note what’s deliberately absent from this chain: the observability trace. SaaS trace retention is days to weeks; HIPAA’s accounting horizon is six years. Retention itself is defined rather than inherited, because the platform has no retention policy of its own: conversation state is ephemeral, the decision and disclosure records ride the EMR trail’s six-year horizon, and provider-side retention is contractually zero under the BAA’s no-training, no-retention terms.

Slide 11

Portability

~55s

On slide: agent code → OTel exporter → LangSmith today, Braintrust and self-hosted Langfuse as plug-compatible alternates.

We trace everything — tool timings, token counts and cost, verification verdicts — in LangSmith today. But portability is a design requirement, not an aspiration, enforced by three rules: agent code emits OpenTelemetry spans and never imports a vendor SDK — LangSmith is an exporter destination, configured, not coded against; the readiness check calls it “trace backend,” a dependency, not a product; and the trace carries no compliance role, so retention limits and migrations never touch the compliance story.

The consequence: moving to Braintrust or self-hosted Langfuse is an exporter-config change plus one adapter file. That “adapter swap, not re-architecture” claim is engineered here, not asserted. The same spans feed the dashboard and the four alerts — latency, error rate, tool failures, and a cross-patient access anomaly alert that gives the detective control from the authorization story an actual detector, since the audit found the platform has none of its own. Each alert documents its on-call response.

Slide 12

Evaluation

~60s

On slide: invariant/boundary/data-quality cards; git-as-source-of-truth synced one-way to the platform.

There is no happy-path-only suite: every eval case exercises a boundary, an invariant, or a regression. Invariants like “every claim carries a valid citation” and “dosing and diagnosis requests are refused.” Boundaries like empty records, injected documents, and questions about a different patient than the open chart.

The most interesting cases came from the data audit, and they’re real, not hypothetical. A patient with no allergy row must yield “no allergies recorded” — never “no allergies” — because empty and NULL are used interchangeably across the patient table. The demo’s own patient 2 has Lisinopril marked active in the prescriptions table and inactive in the problem list, so a test asserts the agent flags the conflict rather than silently picking a side. And zero-dates render as “unknown,” never fed to date math.

Structurally, the suite’s source of truth is the repo: cases are versioned fixtures reviewed in PRs and run in CI on every prompt or tool change. The platform is just the runner and history viewer — datasets sync one way, from git. That keeps the most accumulative, most vendor-sticky asset portable.

Slide 13

Decisions

~50s

On slide: five chosen-versus-rejected rows.

Five decisions, each with the road not taken. Claude, tiered fast-and-strong, over self-hosted open source — self-hosting removes the BAA question but its quality and ops cost isn’t justified in a one-week sprint with BAAs assumed. A minimal explicit tool-use loop over LangGraph or multi-agent — with one agent and six tools, a loop I can fully explain beats a framework I’d debug under deadline. FastAPI with Pydantic contracts on every tool boundary, so malformed data fails at the edge, not mid-conversation.

The one I’d defend hardest: FHIR with the user’s token over direct SQL. SQL would be faster and would bypass every enforcement layer — ACL, scopes, audit — moving authorization into my code. That’s the wrong trade in an EMR. The HTTP-hop cost is real, and it’s paid for by the parallel snapshot. And LangSmith over Braintrust: the BAA criterion tied — both gate it behind Enterprise — so tiebreakers decided, and slide 11 is what makes that choice cheap to revisit.

Slide 14

Scale

~45s

On slide: staircase from 100 to 100K users; cost chips.

Unit economics first: a snapshot is roughly five to fifteen thousand input tokens, call it two to ten cents per interaction — one to two dollars per physician per day. The interesting part is that each order of magnitude has one dominant problem. At a hundred users, the current shape holds. At a thousand, the service goes stateless behind a load balancer with conversation state in Redis — and the interface is already Redis-shaped, so that’s configuration, not redesign — while the FHIR layer becomes the bottleneck. At ten thousand, LLM rate limits dominate, and the lever is pre-computation: a morning batch over the day’s schedule turns interactive queries into warm cache hits. At a hundred thousand, it’s multi-region and per-tenant isolation, and cost becomes a caching architecture problem rather than a per-token one.

Slide 15

Known limits

~65s

On slide: six limitation cards; the security-prerequisite card highlighted.

I want to end with the gaps, because the defensible version of this system is the one whose gaps are documented. No panel-scoped authorization — inherited from OpenEMR; every agent invocation is separately audit-logged and the cross-patient anomaly alert from slide 11 watches for misuse, so detection is real rather than aspirational, and preventive panel scoping with break-glass is roadmap. Grounding is not entailment — the hot path can’t catch a cited-but-misstated claim, so we measure that rate offline and will only add an in-path check if the data justifies the latency. Injection can still bias emphasis. The latency numbers are unvalidated until load testing lands. It’s one persona — physicians; nurses and residents are deferred, and the inherited-authorization design is exactly what makes adding them safe later.

And the red card: three platform security fixes gate the browser panel — a reflected-origin CORS policy, missing session regeneration, and an MFA check the session guard never re-verifies, with session-cookie hardening riding along. These matter more, not less, once the panel adds JavaScript surface to the chart and mints tokens from that session. Until they’re remediated, the panel ships as a same-origin module only. They’re tracked as hardening prerequisites the agent work depends on, not agent features.

Slide 16

Close

~25s

On slide: the invariant, full-screen.

If you remember one sentence: the physician always knows what the agent did — and what it did not — check, and every claim points at a record. Everything else on these slides — read-only tools, inherited authorization, deterministic verification, honest failure banners, swappable vendors — exists to keep that sentence true. Happy to go deeper on any boundary.
